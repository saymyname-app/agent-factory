# Agentic TDD and review workflow — evidence for Q47–Q48

Date: 2026-09-23. Scope: project-agnostic design; primary sources only. Matt's skills below are pinned to commit [`c55ee46`](https://github.com/mattpocock/skills/tree/c55ee46073ed923f86ce59a5eb3b6d895095d1b7); the Sandcastle template is from its moving `main` branch, so its behavior is a separate example, not an interpretation of that skill revision.

## What Matt's pinned method actually says

- [`/to-tickets`](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/to-tickets/SKILL.md) produces independently verifiable vertical slices sized for a fresh context window. [`/ask-matt`](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/ask-matt/SKILL.md) explicitly says to run `/implement` **per ticket**, clearing context between tickets; each `/implement` drives `/tdd` and closes with `/code-review` before committing. Thus review only after the entire Wayfinder-derived feature is **not** the pinned method.
- [`/implement`](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/implement/SKILL.md) says to use TDD where possible at pre-agreed seams, typecheck and run focused tests regularly, run the full suite once at the end, invoke `/code-review`, and commit. It does **not** assign test writing and implementation to different agents or sessions.
- [`/tdd`](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/tdd/SKILL.md) specifies one public-interface test, failing first, then minimal implementation, repeated in vertical slices. It warns against writing all tests before all implementation. Its precise wording calls the loop **red → green**, and places refactoring in the review stage, not each test cycle. Pre-agreed test seams are required. This is a method prescription, not an empirical comparison of agent layouts.
- [`/code-review`](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/code-review/SKILL.md) reviews a diff from a specified fixed point on two independent axes, documented standards and fidelity to the originating issue/spec, with two parallel subagents. It asks for a fixed point if none was supplied. `/implement` does not supply one in its own text; an automated workflow must make the per-ticket comparison base explicit.
- [`/wayfinder`](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/wayfinder/SKILL.md) is a planning map of decisions, not the implementation or review unit. It hands off to `/to-spec` after the fog clears; it does not prescribe a single final review of all tickets.

The [Sandcastle sequential-reviewer template](https://github.com/mattpocock/sandcastle/blob/main/src/templates/sequential-reviewer/main.mts) runs one implementer and then a **different reviewer for each issue**, on a dedicated branch. Its [implement prompt](https://github.com/mattpocock/sandcastle/blob/main/src/templates/sequential-reviewer/implement-prompt.md) asks the same implementer to write a failing test and the code, using “Red → Green → Repeat → Refactor.” Its [review prompt](https://github.com/mattpocock/sandcastle/blob/main/src/templates/sequential-reviewer/review-prompt.md) has the reviewer check intent, tests, security, and maintainability and optionally fix the branch. The template's RGR wording differs from pinned `/tdd`'s explicit placement of refactoring in review; neither source proves one placement better.

## Other first-party practice and empirical limits

- [Anthropic's Claude Code practice](https://www.anthropic.com/engineering/claude-code-best-practices) recommends test-first for readily verifiable work: write tests, confirm red, commit tests, then implement without changing them. It suggests an independent subagent to check overfitting. That is guidance; it does not require a separate **test author**.
- [Anthropic's long-running-agent report](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) explicitly says it remains unclear whether a single general coding agent or specialized agents (including a test agent) perform better across contexts. This directly limits any claim of consensus in favor of a separate test-writing agent.
- A [2026 controlled TDD study](https://arxiv.org/abs/2605.17242) found sizable quality gains for test-based feedback on generated full-stack web apps, but also found protocol choice depended on the agent/model and that a mismatch could erase gains while greatly increasing token cost. Its web-app setting and protocols do **not** settle our choice between one author doing red/green and an independent test author for repository tickets.
- A [2026 observational study of 1.02 million reviewed PRs](https://arxiv.org/abs/2607.13196) associated some AI-agent review patterns with faster decisions but did not find corresponding quality improvement. It compares adoption patterns and PR interactions, not randomized per-ticket versus whole-feature review; it cannot establish that more review calls are better.

## Design implications (inference, not settled facts)

The lowest-complexity starting point consistent with Matt is one implementer doing incremental red/green per ticket, with tests tied to agreed public behavior, followed by an independent two-axis per-ticket review. A separate test-writing agent is a measurable experiment for categories where a test author can work from a stable spec and public seam without pre-writing a brittle horizontal suite. A whole-feature integration check may catch interactions among independently accepted tickets, but would answer a different question than the per-ticket review and needs its own value/cost measurement. The sources above provide **no direct comparison** proving which split or review frequency optimizes accepted quality per token in this Factory.

## Q48 follow-up: selective review and token cost

- Matt's pinned [`/ask-matt`](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/ask-matt/SKILL.md) and [`/implement`](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/implement/SKILL.md) give no risk-based exemption: each implemented ticket ends with `/code-review`. A selective policy is therefore our adaptation, not Matt's method.
- [Anthropic's general agent-design guidance](https://www.anthropic.com/engineering/building-effective-agents) says to add parallel LLM work where subtasks need different perspectives or confidence, while weighing extra cost and latency; it is not a direct study of per-ticket code-review frequency.
- [OpenAI's internal Codex safety practice](https://openai.com/index/running-codex-safely/) makes low-risk routine actions frictionless and raises higher-risk actions for review. This is an analogy for differentiated controls, **not** evidence that skipping low-risk code review is safe.
- [Google's modern code-review case study](https://research.google/pubs/modern-code-review-a-case-study-at-google/) describes lightweight review of code changes at large scale; it does not establish whether AI review can be omitted for selected changes.

Inference for experimentation: retain deterministic verification for every ticket. Initially collect per-ticket independent-review yield and cost on real outcomes; then allow a predefined, proven low-risk class to skip model review while still sampling skipped tickets and tracking later defects/rework. Novel behavior, security/privacy/data-lifecycle changes, cross-ticket contracts, uncertain test oracles, and unusually broad diffs should remain review candidates. Consolidating Matt's two independent axes into one reviewer could save context duplication but may lose independent perspective; measure rather than assume. The available first-party sources do not provide a universal skip threshold or a controlled comparison of these policies.
