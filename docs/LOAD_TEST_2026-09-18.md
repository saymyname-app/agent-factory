# Factory load test — 2026-09-18 (af-liak1)

## What this is

`tests/factory-load-test.sh` (new, this change) drives real CPU burn plus
parallel `gc bd` readers for a fixed window and samples
`saymyname-product-status` and `mayor-campaign sentinel` wall-clock durations
throughout, checking each command's median against half its own timeout
(the same threshold the acceptance criteria for af-liak1 specifies), plus
counting `order.failed` events during the window.

## Why the full N=6/8 run was not executed here

This bead's own premise is the 2026-09-17/18 incident: WSL load 15-20 on 12
vCPU, ~500 MB free RAM. At the moment this test was built and smoke-tested
(2026-09-18 16:39-16:41 CEST), the host was **already** at:

```
$ uptime
 16:39:59 up 19:04,  2 users,  load average: 7.32, 10.52, 9.92
$ free -h
               total        used        free      shared  buff/cache   available
Mem:           7.8Gi       3.7Gi       862Mi        25Mi       3.4Gi       4.1Gi
```

i.e. load average already in the 7-10 range with well under 1 GiB free, on
the same shared host actively running the Mayor, this pool worker, and other
concurrent sessions doing real work. Deliberately adding a second, larger
synthetic load spike (N=6 CPU burners + N=6 `gc bd` readers, sustained for
minutes) on top of that would not *measure* the incident under controlled
conditions — it would very likely *cause* it again, on production, while real
work is in flight. That is a production-affecting, hard-to-reverse action
(other sessions could be starved, killed by OOM, or produce corrupted state)
and was not something to trigger unilaterally without Benjamin's go-ahead.

**Recommendation:** run the N=4/6/8 sweep during a maintenance window with
the Factory idle (Mayor and pool workers drained), or on a dedicated
non-production host with the same core/RAM shape. `tests/factory-load-test.sh
-n 6 -w 120` is ready to run as soon as such a window is scheduled — see
"How to run the full sweep" below.

## What was actually measured

A single, minimal smoke-test invocation (`-n 1 -w 10`, i.e. the smallest N
the script supports — one CPU burner, one `gc bd list` loop) was run against
the live host at the load shown above, to (a) prove the script's mechanics
are correct and (b) get one real data point under presently-loaded
conditions. It produced exactly one real invocation each of
`saymyname-product-status` and `mayor-campaign sentinel` (the sentinel ran
its normal production tick as a side effect — it is not a dry-run command):

| command | duration | timeout | half-timeout | verdict |
|---|---|---|---|---|
| `saymyname-product-status` | 14.443s | 20s | 10s | **exceeds** half-timeout |
| `mayor-campaign sentinel` | 28.469s | 50s | 25s | **exceeds** half-timeout |
| `order.failed` events | 0 | — | — | pass |

Numbers, not adjectives: at *today's* ambient host load (7-10, no
deliberately added stress), both commands already ran past half their
timeout budget, with zero extra synthetic load from this test. This says the
margin PR #87/#90/#103 bought is thinner than "one bad night" — the host
right now, mid-afternoon, on ordinary Factory activity, is close to the
threshold these fixes were sized against. This is evidence for prioritizing
the scheduled maintenance-window run, not a substitute for it.

## Session-naming audit (`max_active_sessions=1` canonical-singleton concern)

This part of the acceptance criteria needed no synthetic load, so it was
completed in full against live, real state.

**Ground truth, from `gc session list --json` today:**

```
name: "claude-standard-2"        (pool slot alias; max_active_sessions=2 today)
session_name: "claude-standard-af-n8hc5"   (embeds the unique session id)

name: "claude-reviewer"          (pool slot alias; max_active_sessions=1 today)
session_name: "claude-reviewer-af-3o4ei"   (embeds the unique session id)
```

Two distinct identity strings exist per session:

- **pool slot alias** (`name`/`agent_name`/`alias`, and the `$GC_AGENT` env
  var inside a session): gets a numeric suffix (`-2`) only when the pool's
  `max_active_sessions` is greater than 1. With `claude-reviewer` (already
  `max_active_sessions=1`), the alias carries **no** suffix today — this *is*
  the "canonical singleton" the bead is worried about, and it already exists
  in production for one pool.
- **`gc.session_name`** (the field on bead metadata, and the `session_name`
  key in `gc session list`/`gc events`): **always** embeds the actual unique
  session id (`af-xxxxx`) regardless of pool size. It was never slot-number
  based.

Checked each named script against which identity it actually reads:

| script | what it reads | slot-alias dependent? |
|---|---|---|
| `bin/provider-failover` (pane reading) | `session.get("session_name")` — the id-embedding field | No |
| `bin/on-session-stranded` | `.payload.session_name // .session_id` from the event — reported verbatim, not pattern-matched | No |
| `bin/saymyname-product-status` (`CURRENT_AGENT`) | `gc.session_name` bead metadata, then asserts `bd list --assignee="$session_name"` returns a live count `<= 1` (`die "... is not unique in Gas City."` otherwise) | No — the uniqueness check is against the id-embedding `session_name`, which stays unique per session no matter how many slots the pool has |

Repo-wide grep for `GC_AGENT` (the slot-alias env var) and for any
slot-number pattern match (`claude-[0-9]`, etc.) against agent/session names
turned up **no** consumer in `bin/` or `lib/` — nothing in this codebase
keys logic off the pool slot alias's numeric suffix.

**Finding: collapsing `max_active_sessions` to 1 for the `claude-standard`
pool does not break any of the three named scripts**, because none of them
actually depend on the slot-alias naming scheme that would change — they key
off `gc.session_name`, which was already id-unique before this change and
stays id-unique after it. No follow-up bead is needed for this part.

This does not by itself certify `max_active_sessions=1` is *safe* in the
throughput/liveness sense the bead also asks about (measure (a): timeouts
under real load) — that is exactly the deferred N=6/8 sweep above, run once
at the merged cap=2 and once against a `max_active_sessions=1` config copy.

## How to run the full sweep (once a maintenance window exists)

```bash
# Drain the Mayor and pool workers first, or run on a dedicated host with the
# same core/RAM shape as production.
tests/factory-load-test.sh -n 6 -w 120 -o /tmp/load-cap2
# repeat against a max_active_sessions=1 config copy (city.toml patched, not
# the live one) for the second measurement the acceptance criteria asks for.
```

Append both runs' result tables and `uptime`/`free -h` before/after to this
file, dated, and close out the remaining half of af-liak1's acceptance
criteria.
